The results above show what the method achieves on the metrics we defined.
Four limitations bound how far those results should be read.

\subsection{Graph structure constraints}

\begin{quote}\small\itshape
\begin{itemize}
\item Graph structure constraints --> incomplete semntic definition, which our tokenizer can not do shit
\end{itemize}
\end{quote}

The context tree and the coverage score (Section~\ref{sec:method}) can only
ever reflect the relationships that are actually encoded in the graph. Where
SNOMED~CT's own definition of a concept is incomplete -- a relevant attribute
simply not modeled as an outgoing edge -- the tokenizer cannot compensate for
this: an under-specified concept will look under-specified in its context
tree regardless of which token set $T$ is chosen. \doubt{I read "our
tokenizer can not do shit" as "our method has no way to fix or detect this,"
which is what the sentence above says -- flag if you meant something more
specific, e.g.\ a particular class of missing relationships you've already
run into.}

\subsection{Transductive method}

\begin{quote}\small\itshape
\begin{itemize}
\item transductive method for toke selection
\end{itemize}
\end{quote}

A second limitation concerns how the method generalizes beyond the mapped
set it was run on. Token selection (Section~\ref{sec:method:selection}) is transductive: it
optimizes coverage for a fixed, known $M$, and a token set selected for one
institution's mapped concepts is not guaranteed to transfer to a different
mapped set without re-running selection.

\subsection{No external validation on a clinical task}

\begin{quote}\small\itshape
\begin{itemize}
\item No external validation on clinical task
\end{itemize}
\end{quote}

A third, related limitation concerns what "quality" was actually validated
against. This paper evaluates tokenization quality intrinsically (the metrics of
Section~\ref{sec:method:metrics}) and, directly, via clinical-expert
acceptability ratings of the tokenized representation against the original
concept (Section~\ref{sec:method:expert-eval}). What it does not do is
validate the tokenization on an actual downstream, assistive clinical
decision task -- i.e.\ show that a model trained on this reduced vocabulary
performs a real clinical decision-support function (diagnosis support, risk
prediction, etc.) at least as well as one trained on an alternative
vocabulary. \notetoself{per your feedback, this is a distinct claim from the
expert acceptability evaluation in Method -- that one is about representation
fidelity judged by an expert, this one is about end-task clinical utility,
and only the first is in scope for this paper.}

\subsection{Requires a DAG}

\begin{quote}\small\itshape
\begin{itemize}
\item Not working on Non-DAG
\end{itemize}
\end{quote}

Finally, the method's applicability is bounded by the same structural
assumption made throughout the paper. The tokenizer's core mechanism -- \texttt{IS\_A} transparency, non-\texttt{IS\_A}
subcontexts, and the coverage recursion's reliance on well-defined finite hop
distances -- assumes an acyclic graph. It does not extend as-is to a
vocabulary with cycles, or to a general knowledge graph where the
child/parent asymmetry of Section~\ref{sec:background} does not hold.
